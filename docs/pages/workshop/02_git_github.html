6  Version control, collaboration and sharing

5–17 minutes · Git and GitHub

6.1 Learning objectives

By the end of this activity, you should be able to inspect repository changes, make a focused commit on a branch, and describe how a pull request supports review. Your output is a committed provenance note for the teaching dataset.

Prerequisite: the project copy from preparation. Run the shell blocks in the Terminal at the project root.

6.2 Why this matters

Git tracks changes to files through commits and branches. GitHub hosts Git repositories and adds collaboration tools such as issues and pull requests. A commit records a change; a useful message explains its purpose.

For our correlation example, a small provenance note makes the dataset source and the decision to preserve the raw file visible to collaborators.

6.3 Inspect the project and create a branch

Allow about two minutes. Check your current directory, branch, and remote.

git status --short
git branch --show-current
git remote -v

If you downloaded the data during preparation, data/ may be untracked. That is expected at this stage. Inspect existing work before proceeding, and leave changes you do not intend to commit in place.

For the sharing exercise, origin should point to your fork. If you cloned the teaching repository directly, you can complete the local commit exercise and watch the instructor demonstrate sharing from a fork.

Create a working branch:

git switch -c workshop/health-wellbeing

If this branch already exists from an earlier attempt, inspect it and switch to it rather than creating it again.

6.4 Create a provenance note

Allow about four minutes. Create WORKSHOP_NOTES.md in the project root using your editor. Use the following as a starting point, replacing the author and retrieval-date placeholders with your own information.

# Health and well-being: workshop notes

Author: YOUR NAME

## Research question

What association between health and well-being is reported across the studies?

## Data source

- Dataset: HealthWellbeing.
- Book: Harrer, Cuijpers, Furukawa, and Ebert (2021), section 4.2.4.
- Book URL: https://doing-meta.guide/pooling-es#correlations
- Dataset documentation: https://dmetar.protectlab.org/reference/healthwellbeing
- Download: https://www.protectlab.org/meta-analysis-in-r/data/healthwellbeing.rda
- Retrieved: YYYY-MM-DD
- Raw file: data/raw/healthwellbeing.rda
- MD5: 0d74964b0b7168379a2b015cb648b326

## Decisions

Preserve the raw file unchanged. Keep derived data and analysis outputs separate.
Check upstream reuse terms before redistributing data.

Check the note against the source you actually used. If you received the file from the instructor, record that transfer and the verified checksum as well. The original review is Ngamaba, Panagioti, and Armitage (2017).

6.5 Stage and commit one change

Allow about three minutes. Stage the note explicitly and inspect what will be committed. Newly created, untracked files do not appear in ordinary git diff; after staging, inspect them with git diff --cached.

git add WORKSHOP_NOTES.md
git diff --cached --name-only
git diff --cached -- WORKSHOP_NOTES.md

Confirm that the staged list contains only changes you intend to include. Then make the commit:

git commit -m "docs(workshop): record HealthWellbeing data source"
git log -1 --oneline
git status --short

If Git asks for an identity, configure your name and preferred commit email for this repository, then retry. The note should now be committed. The downloaded raw file may still be untracked; it was not included by staging the note.

6.6 Share and request review

Allow about three minutes, including the instructor demonstration. If origin is your fork and GitHub authentication is ready:

git push --set-upstream origin workshop/health-wellbeing

On GitHub, open a pull request within your fork, comparing this branch with its main branch. Inspect the Files changed view and ask a partner to check that the data source is identifiable and the note describes what you actually did. Keep the exercise pull request in your fork.

For a substantive contribution to the teaching repository, follow its contribution guidance and AI assistance policy. A pull request provides a place for review; creating one does not mean that human review is complete.

6.7 Checkpoint

  • You can identify your current branch and its remote repository.
  • Your latest commit contains WORKSHOP_NOTES.md with the dataset source.
  • You can explain the difference between a local commit, a push, and a pull request.

If sharing is unavailable, keep the local commit and inspect the instructor’s pull request. The learning checkpoint does not require a live merge.

Takeaway: make focused changes whose purpose and provenance are clear. Next, record the computational environment.

12  GitHub releases, Zenodo and archiving

Conceptual · GitHub releases and Zenodo

12.1 Introduction

In this overview, we start from the report you just updated. We work out what a colleague would need to rerun it, then see how a GitHub release and an archived Zenodo record keep those materials together and citable. We finish with what to do when the data cannot be shared.

Question for the room. Think of the report you just rendered. What would a colleague need to rerun it exactly and get the same numbers?

12.2 Decide what to archive

Each part of workspace/report.html points to files a colleague would need.

In your report Files that support it Where they go
Methods and results .here, workspace/report.qmd, and outputs/health-wellbeing/meta-summary.csv Track the project-root marker and report source. Attach the summary and the rendered HTML.
Pipeline script MD5, variance estimator, and interval method workspace/_targets.R, plus the support and preparation scripts it relies on Track.
Upstream snapshot, raw and selected input MD5s, and inclusion rule The data source and upstream notice in data/raw/, and the dataset metadata Track. Attach any FAIR assessment record.
Dataset and predictive model pin versions analysis-data-version.txt, dataset-versions.csv, predictive-model-version.txt, and the pins Attach the version files. Attach the pins if permitted and needed to preserve the exact stored versions.
R and meta versions renv.lock, the Dockerfile or image reference, and the session record Track the lockfile and Dockerfile. Attach the session record.

The files can be managed with version control using git.

12.3 Releases on GitHub

A Git commit identifies a repository revision. A GitHub release gives a tagged revision a name and a place for release notes and attached files.

An archiving service such as Zenodo can store a copy of selected files and issue a Digital Object Identifier (DOI). An archive makes the cited files available under the access conditions of that record (Zenodo, n.d.c).

One release ties your pipeline, report source, lockfile, and metadata together at one tagged revision. A reader can then retrieve that exact combination rather than the repository’s latest state. In the workshop repository, preparing a release follows the steps we have used throughout the session:

  1. Record the changes in the CHANGELOG.md and commit that entry.
  2. Tag the commit and publish a release with notes on the releases page.
  3. Publishing the release builds and pushes the RStudio and Binder Docker images.
  4. With Zenodo integration enabled for the repository, Zenodo also archives the tagged files.

12.4 Inspect a Zenodo record

Workshop archive · GitHub releases

Open the workshop’s Zenodo record (Bristow and Liang 2026). Find the creators, access conditions, the ZIP of the archived revision, and the list of versions. The concept DOI, 10.5281/zenodo.24342489, represents all versions and always resolves to the latest one.

The workshop has three connected locations:

Resource Role
Workshop website Read the published workshop materials.
GitHub repository Find the source files, history, and releases used to publish the site.
Zenodo archive Find and download the archived releases.

Each version’s related identifier points to the GitHub release tag it archives.

As a follow-up, assess the workshop’s software record using the concept DOI. Select the FAIR for Research Software metrics in rfair. The FAIR lesson used research-data metrics for the HealthWellbeing snapshot (Sofi-Mahmudi 2026).

archive <- rfair::assess_fair(
  "https://doi.org/10.5281/zenodo.24342489",
  metric_version = "0.7_software", timeout = 10, max_time = 60
)

12.5 Supplementary: When the data cannot be shared

Open science can include restricted-access data: you can share the methods, code, metadata, and access conditions while restricting the original observations.

Synthetic data generated with synthpop can help others test whether a workflow runs. It does not let them verify findings computed from data that cannot be accessed, and it does not guarantee privacy. The supplementary synthetic data exercise works through an example after the workshop.

12.7 After the workshop: archive your own releases

To archive releases of your own repository, follow Zenodo’s Enable a repository guide:

  1. Connect your GitHub account to Zenodo if it is not already linked.
  2. In Zenodo’s profile menu, select GitHub.
  3. Select Sync now to refresh the list of repositories.
  4. Find the repository you maintain and enable its slider.
  5. Refresh the page and check that the repository is enabled.

Once connected, publishing a new GitHub release triggers automatic archiving in Zenodo. Inspect the resulting version record, its DOI, metadata, and downloadable files after each release. The Sync now control refreshes the repository list; published releases are the events that create new archives.

7  FAIR data documentation and assessment

Demonstration · dataspice and rfair

7.1 What would a collaborator need?

We use the FAIR principles to document the HealthWellbeing teaching snapshot and assess what software can discover about it. The table gives one question to ask for each principle (GO FAIR, n.d.).

Principle Ask Example for this dataset
Findable Can someone locate and identify it? A named record with a stable identifier and searchable metadata.
Accessible How can someone retrieve it, and on what terms? A working download link with a statement of the access terms, or clear instructions for requesting access.
Interoperable Can people and software interpret its structure? Use shared metadata terms such as Schema.org and describe the variables and their units.
Reusable Can someone judge whether it suits their project? Explain the source, the unit of observation, and the licence.

7.2 Describe the snapshot with dataspice

Four prepared CSV files under data/metadata/health-wellbeing/ record the title and licence, creator, download link, and variables. n in attributes.csv (line 4) says that each row of the data describes one study and n is the sample size within that study. The teaching snapshot has 29 rows and five variables (Harrer et al., n.d.).

file.edit(
  file.path("data", "metadata", "health-wellbeing", "attributes.csv")
)

dataspice combines the CSV files into a Schema.org JSON-LD record (Boettiger et al. 2026). The excerpt shows the title, licence, download link, and variables, so you can see that its meaning and unit survive the export.

7.3 Assess the snapshot with rfair

rfair takes a URL or persistent identifier and applies a set of tests to the metadata it can retrieve (Sofi-Mahmudi 2026).

First, assess the HealthWellbeing.rda file:

metadata_file <- file.path("data", "metadata", "health-wellbeing", "dataspice.json")
metadata <- jsonlite::read_json(metadata_file)
snapshot_url <- metadata$distribution[[1L]]$contentUrl
baseline <- rfair::assess_fair(
  snapshot_url, metric_version = "0.8", timeout = 6, max_time = 30
)

And follow up with a comparison of the original evaluation against this new evaluation:

comparison <- rfair::fair_compare(baseline, enriched)
metrics <- c("FsF-F1-02MD", "FsF-A1-01M", "FsF-I1-01M", "FsF-R1.1-01M")
comparison[comparison$metric_identifier %in% metrics,
           c("metric_identifier", "status_a", "status_b")]

One metric from each principle shows what changed and what stayed the same.

Metric Download URL alone With the JSON-LD supplied
Persistent identifier (FsF-F1-02MD) Fail Fail
Access information in metadata (FsF-A1-01M) Fail Fail
Formal language for metadata (FsF-I1-01M) Fail Pass
Licence in metadata (FsF-R1.1-01M) Fail Pass

The file downloaded successfully in both runs, yet the access check (FsF-A1-01M) failed both times. Why? What would you add to the public record so a reader knows how to get the file?

One possible answer

This metric looks for access information in the metadata. A working link shows that the assessor could download the file at that moment. It does not tell a reader whether anyone can download it, whether they need to sign in, or whether they must request approval.

For this snapshot, a statement such as “Public download, no sign-in required” beside the URL would answer the question. Schema.org has isAccessibleForFree and conditionsOfAccess properties for this. For a restricted dataset, the record could say who may access the data and how to request it. Rerun the assessment to check whether a particular metric version recognises the statement.

7.4 Checkpoint

The record now says what the data mean and how to get them. It does not say which version of the data produced a given result. Next, we identify that version. Data and model versioning
